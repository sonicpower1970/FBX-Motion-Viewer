# v0.2.3 — VFX Burn-in Overlay

BURN-IN Filename / Frame independently enable a new viewport overlay. Both default to OFF. Existing toolbar filename and Timeline frame fields remain unchanged. When enabled, the navigation hint moves upward to avoid overlap. No asset means no preview burn-in.

## Shared renderer

`src/overlay/BurnInRenderer.ts` contains settings, basename sanitization, Timeline-compatible frame counter, text fitting and drawing. The preview uses a transparent Canvas 2D over the WebGL canvas. Export draws the rendered WebGL frame into a separate Canvas 2D, then uses the exact same burn-in renderer before the encoder captures that canvas. With both settings OFF the original direct WebGL-to-encoder path remains in use. No HTML capture, screen recording or external service is involved.

The filename is sanitized to the last segment of either slash convention, regardless of File.name normally already being a basename. It never includes local directories. Filename fitting measures actual browser text width, scales font down to its minimum, then uses a middle ellipsis only if necessary. Code points are preserved and the filename suffix, including .fbx when space permits, is retained. The maximum filename width is 63% of the output. The counter has a separate right-hand region.

Font: 500-weight Arial/sans-serif, 24px at 1080 high, minimum filename size 14px at 1080 high. Safe margins are 32px at 1080 high. Font, margin and thin dark outline scale with actual canvas height for both preview and export, including device-pixel-ratio. Text is modest, off-white and has no background panel. Exceptionally narrow outputs may shrink the counter further to prevent overlap. Frame numbers use the same displayFrame/endFrame functions as the Timeline, with at least four digits and additional digits as needed. Start-frame offsets are presentation-only and support future 1/1001/etc. settings.

Every live render reads exact playback time, rather than the throttled React snapshot. Every offline output frame evaluates animation at its scheduled time, renders Three.js, draws current burn-in text, then awaits encoding. The final partial-frame endpoint uses the Timeline end-frame convention. Follow, start Fit, loop handling, save picker and state restoration are unchanged.

Frame Guide remains a separate HTML composition guide and is never exported. Burn-in anchors to the entire current viewport/output, not to the contained Frame Guide rectangle. Relative height-based text/margins match across resolutions; horizontal layout can differ when viewport and export aspects differ. Guide visibility has no effect on burn-in settings or export.

## Limitations and real-machine checks

Platform font fallback/rasterization can differ, especially for non-Latin filenames; preview/export on the same browser use the same renderer. Very small viewports intentionally show small text to preserve relative export sizing. Extremely long names require middle ellipsis. Canvas compositing adds one output-sized RGBA buffer and a per-frame copy while burn-in is enabled; large resolutions increase memory and export time, but never intentionally drop frames. Existing 512 MiB encoded-output cap and WebCodecs/H.264 availability limits remain.

On Windows/macOS/Linux Chrome, check all four Filename/Frame combinations; ordinary/Japanese/very long filenames; frame 0/middle/end/loop/step/scrub; Follow ON and pause/resume restoration; 720p/1080p/Current Viewport output; resize and device scaling; Frame Guide ON while verifying that only burn-in appears in the MP4. Native file dialogs and OS/GPU differences still require real-machine acceptance outside this Apple Silicon Mac environment.
